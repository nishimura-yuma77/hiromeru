# バックエンド コーディング規約（v0.1 雛形）

対象: hiromeru（AI支援型Xマーケティングシステム）MVP のバックエンド（Python）

本書は雛形である。方針の見出しと要点を書き、チームで決めていない箇所は **【要決定】** と明記している。ツール・数値の決定事項と未決事項は付録Bにまとめている（2026-09-21 時点）。決まった項目から【要決定】を外し、確定内容に書き換える。

## 0. 位置づけ

### 0.1 優先順位

規約と設計書が食い違う場合は、次の順で上のものを正とする。

1. `DATABASE.dbml`（データ構造と制約）
2. `API_DESIGN.md`（APIの Request / Response / エラー）
3. `AGENT_DESIGN.md`、`USECASE.md`（Agent・業務フロー）
4. 本書（コードの書き方）

本書は「どう書くか」を定める。「何を作るか」は上記の設計書に従う。

### 0.2 ルールの強さ

| 表記 | 意味 |
| --- | --- |
| 必須 | 守る。例外はレビューで合意し、コメントで理由を残す |
| 推奨 | 原則守る。守らない場合は理由を説明できること |
| 【要決定】 | 未決定。決定するまでは暫定の既定値に従う |

## 1. 基本方針

1. **読みやすさを優先する。** 短く書くより、読み手が迷わない書き方を選ぶ。
2. **正しさは型と検証で守る。** 入力は境界（API・外部API・DB）で検証し、内側では検証済みの型を使う。
3. **失敗を隠さない。** 例外の握りつぶし、失敗を成功として扱う実装を禁止する。
4. **機密を書かない。** 認証情報、トークン、個人情報をコード、ログ、テストデータへ書かない。
5. **決定論的に書く。** 時刻、乱数、外部APIへの依存は差し替えられる形にし、テストで固定できるようにする。

## 3. 命名規則

| 対象 | 規則 | 例 |
| --- | --- | --- |
| パッケージ・モジュール | `snake_case` | `campaign_service.py` |
| クラス | `PascalCase` | `CampaignService` |
| 関数・変数 | `snake_case`。動詞で始める（関数） | `publish_post()` |
| 定数 | `UPPER_SNAKE_CASE` | `MAX_RETRY_COUNT` |
| 非公開 | 先頭に `_` | `_build_utm()` |
| 真偽値 | `is_` / `has_` / `can_` で始める | `is_archived` |
| DB のテーブル・カラム | `snake_case`。`DATABASE.dbml` と完全に一致させる | `post_tracking_links` |
| JSON のキー | `snake_case`（`API_DESIGN.md` に合わせる） | `campaign_id` |
| エラーコード | `UPPER_SNAKE_CASE`。`API_DESIGN.md` に登録してから使う | `INVALID_X_POST` |

- 必須: 日時は `_at`（例: `created_at`）、ID は `_id`（例: `company_id`）で終える。
- 必須: 単位を持つ値は名前に単位を含める（例: `response_time_ms`）。
- 必須: 略語は一般的なもの（`id`、`url`、`utm`）に限る。独自略語を作らない。
- 推奨: 用語は `DATABASE.dbml` と設計書の語彙に合わせる（Campaign、Post、Turn、Item など）。同じ概念に別名を付けない。

## 4. コードスタイル

- 必須: `ruff format` の出力に従う。手動の整形議論はしない。
- 必須: 1行の長さは 100 文字とする（`ruff` の `line-length = 100`）。
- 必須: import は「標準ライブラリ → サードパーティ → 自プロジェクト」の順で、ruff に整列させる。`from x import *` は禁止。
- 必須: 公開関数・メソッドには型ヒントを付ける。`Any` は原則禁止とし、使う場合は理由をコメントに書く。
- 必須: ミュータブルなデフォルト引数（`def f(x=[])`）を使わない。
- 必須: マジックナンバー・文字列を直書きしない。名前付き定数か設定値にする。
- 必須: 日時は **タイムゾーン付き（UTC）** で扱う。ナイーブな `datetime` を使わない。`datetime.now()` を直接呼ばず、時刻取得の関数を注入する（テストで固定するため）。
- 必須: 金額（`cost_usd` など）は `Decimal` を使い、`float` を使わない。
- 推奨: 早期リターンで入れ子を浅くする（目安: 3 段まで）。
- 推奨: 1 関数は 1 つの責務にする（目安: 50 行以内）。
- 推奨: データの入れ物は `dataclass(frozen=True)` または Pydantic モデルにする。`dict` を型なしで受け渡ししない。
- 推奨: 状態や種別は `Enum` で表す。DBML の enum と値を一致させる。

## 5. コメント・docstring

- 必須: コメントと docstring は **日本語** で書く（`DATABASE.dbml` と設計書に合わせる）。
- 必須: コメントは「なぜそうするか」を書く。コードを読めば分かる「何をしているか」は書かない。
- 必須: 公開関数・クラスには docstring を付ける。要約は 1 行で、必要なら引数・戻り値・例外を書く。docstring の書式は Google スタイルとする（`ruff` の `pydocstyle` で `convention = "google"` を指定）。
- 必須: 設計書に由来する制約は、対応する設計書の箇所をコメントで示す（例: `# DATABASE.dbml: 埋め込み生成に失敗したら施策を保存しない`）。
- 必須: TODO は `TODO(担当者): 内容 #issue番号` の形式で書く。担当者と issue がない TODO は残さない。
- 禁止: コメントアウトしたコードの残置。履歴は Git に残る。

```python
def build_tracked_url(landing_url: str, campaign_id: int, action_id: str) -> str:
    """遷移先URLにUTMパラメータを付与したURLを返す。

    LLMは使わず、決定論的に生成する。
    """
```

## 6. ディレクトリ構成とレイヤー

### 6.1 構成

```text
src/hiromeru/
  api/            # HTTP境界。ルーター、Request/Response のスキーマ、認証依存
  services/       # 業務処理（ユースケース）。トランザクション境界を持つ
  repositories/   # DBアクセス。SQLはここにだけ書く
  models/         # DBのテーブル定義（DATABASE.dbml と1対1）
  domain/         # 外部に依存しない業務ルール、値オブジェクト、Enum
  clients/        # 外部APIのアダプタ（X、GA4、OrcaRouter、Embedding）
  agents/         # Agent、Tool、Context構築
  core/           # 設定、ログ、エラー基底、時刻・ID生成などの共通部品
tests/
  unit/
  integration/
migrations/
```

### 6.2 依存の向き

`api → services → repositories → models`。`services` は `clients`、`domain` を使ってよい。

- 必須: 下位から上位を import しない（`repositories` が `services` を import しない、など）。
- 必須: SQL とセッション操作は `repositories` にだけ書く。`api` と `services` に SQL を書かない。
- 必須: 外部APIの呼び出しは `clients` にだけ書く。`services` は `clients` のインターフェース（Protocol）越しに呼び、テストで差し替えられるようにする。
- 必須: `api` は HTTP の変換（入力の検証、ステータスコード、Response の組み立て）だけを行い、業務判断をしない。
- 必須: 業務ルールは `domain` または `services` に書く。`api` と `repositories` に書かない。
- 推奨: 循環 import は設計の見直しで解消する（関数内 import で逃げない）。

## 7. API層

- 必須: パスは `/api/v1` 配下とする。Request / Response の形は `API_DESIGN.md` に従う。
- 必須: Request は Pydantic モデルで検証する。`company_id`、`marketer_id` などの権限に関わる値は Request Body から受け取らず、認証済みの実行コンテキストから決める。
- 必須: 他社のリソースは「存在しない」として扱う（`API_DESIGN.md` に合わせる）。所有権の検証は Repository 呼び出しの前に行うか、クエリの条件に含める。
- 必須: ルーターの関数には業務処理を書かず、Service を 1 回呼ぶだけにする。
- 必須: 認証は、署名付き Cookie（ステートレス）で行う。Cookie は `HttpOnly`、`Secure`、`SameSite=Lax` とし、`marketer_id` と有効期限を署名して持たせる。署名鍵は設定値（環境変数）から読み込む。
- 必須: 有効期限は、アイドル 8 時間と絶対上限 7 日とする。操作のたびに Cookie を発行し直してアイドル期限を延長し、絶対上限（ログインから 7 日）は延長しない。
- 必須: 状態を変更する API（POST / PATCH / DELETE）には、次の 2 つの CSRF 対策をどちらも適用する。
  - `Origin` / `Referer` ヘッダーを、許可リストと照合する。
  - 署名付きのダブルサブミットトークン（Cookie の値と `X-CSRF-Token` ヘッダーを照合）を検証する。
- 必須: ユーザー登録の API は作らない。ユーザー・会社・マーケターは、初期データ投入のスクリプトで作成する。
- 推奨: 認証の失敗は、メールアドレスが存在しない場合とパスワードが違う場合を区別せず、同じ応答にする。
- 推奨: 例外を HTTP レスポンスへ変換する処理は 1 か所（例外ハンドラ）に集約する。

## 8. エラー処理

### 8.1 例外の設計

- 必須: 業務エラーは、共通の基底クラス `AppError` を継承した例外で表す。`code`、利用者向けの `message`、`retryable` を持たせる。
- 必須: エラーコードは `API_DESIGN.md` の一覧に登録されたものだけを使う。新しいコードは、先に設計書へ追加する。
- 必須: 例外は「業務エラー」（想定内、4xx 相当）と「システムエラー」（想定外、5xx 相当）を区別する。

```python
class AppError(Exception):
    code: str = "INTERNAL_ERROR"
    retryable: bool = False

    def __init__(self, message: str) -> None:
        super().__init__(message)
        self.message = message  # 利用者に返せる、マスク済みの文言だけを入れる
```

### 8.2 ルール

- 禁止: `except:`、`except Exception: pass`。例外を握りつぶさない。
- 必須: 捕捉するのは、その場で処理できる例外だけにする。処理できない場合は、原因を保持したまま（`raise ... from e`）上位へ渡す。
- 必須: 例外を変換する場所は境界（`clients` と `api`）に限る。内部の層では変換しない。
- 必須: 利用者に返すメッセージには、内部情報（SQL、スタックトレース、認証情報）を含めない。
- 必須: 失敗を成功として扱わない。処理の一部が失敗した場合、部分成功として返さず、失敗の内容を呼び出し元へ伝える。
- 必須: 入力の検証エラーは 400 系、業務条件の違反は 409 / 422 系など、`API_DESIGN.md` のステータス表に従う。

### 8.3 外部API呼び出し

- 必須: すべての外部API呼び出しにタイムアウトを設定する。
- 必須: 再試行するのは一時的なエラー（429、5xx、タイムアウト）だけにする。認可・入力・業務条件のエラーは再試行しない。上限は最大 3 回とし、待ち時間は指数バックオフ（ジッター付き）にする。
- 必須: **副作用のある呼び出し**（例: 外部への投稿）は、結果が不明な場合に自動再試行しない。
- 必須: 外部APIのエラーは、`clients` で自プロジェクトの例外（`UPSTREAM_ERROR` など）に変換し、認証情報を含めない。

## 9. ログ

- 必須: `print` を使わず、標準の `logging`（または採用する構造化ログ）を使う。
- 必須: 本番のログは構造化（JSON）とし、ライブラリは `structlog` を使う。
- 必須: リクエストごとに `request_id` を付与し、可能な範囲で `session_id`、`turn_id` も付ける。
- 必須: ログレベルの使い分け:

| レベル | 使い方 |
| --- | --- |
| ERROR | 対応が必要な失敗。アラート対象 |
| WARNING | 想定内だが注意が必要な事象（再試行、縮退動作） |
| INFO | 業務上の重要な区切り（処理の開始・完了） |
| DEBUG | 開発時の詳細。本番では出さない |

- 必須: **次の情報をログに出さない。** APIキー、アクセストークン、Cookie、パスワード、個人を特定できる情報。エラーの内容も、マスクしてから出す。
- 必須: **LLMの入出力の本文（プロンプト・応答）をアプリケーションログに出さない。** 出してよいのは、`turn_id`、`llm_call_id`、トークン数、コスト、応答時間、エラーコードなどのメタデータだけとする。DEBUG レベルでも本文は出さない。
- 必須: 会話の本文は `agent_items`（DB。マスク済み・変更不可）で確認する（SC-09 の実行履歴）。ログとDBで同じ内容を二重に持たない。
- 必須: ユーザー入力（フォームの値、Request Body）をログへ出す場合は、保存前にマスクし、必要な項目だけを出す。
- 必須: 例外をログに出すときは 1 か所（境界）で 1 回だけ出し、同じ例外を層ごとに重複して出さない。
- 推奨: ログメッセージは、検索しやすい固定の文言にし、可変の値は構造化フィールドへ入れる。

## 10. 設定とシークレット

- 必須: 設定は環境変数から読み込み、型付きの設定クラス（`pydantic-settings` など）で検証する。起動時に検証し、足りなければ起動を失敗させる。
- 必須: シークレット（DB接続情報、X・GA4・OrcaRouter の認証情報）をコードとリポジトリに含めない。`.env` はコミットしない（`.gitignore` に含める）。
- 必須: 設定値はコード内で `os.environ` を直接参照せず、設定クラス経由で参照する。
- 推奨: 上限値（ステップ数、コスト、再試行回数など）は、コードに直書きせず設定値にする。

## 11. 非同期・並行処理

- 必須: **非同期（`async def`）で統一する。** 同期関数との混在は、下記の例外を除き禁止する。
- 必須: 使う部品は次のとおり。

| 用途 | 使うもの |
| --- | --- |
| Web | FastAPI（`async def` のルーター） |
| DB | SQLAlchemy 2.0 の非同期API（`AsyncEngine`、`AsyncSession`）+ psycopg（v3）の非同期接続 |
| 外部API | `httpx.AsyncClient` |
| テスト | `pytest-asyncio`（14 章） |

- 必須: 非同期関数の中でブロッキング処理（同期のHTTP、同期のDBドライバ、`time.sleep`、重いCPU処理）を呼ばない。やむを得ない場合は `asyncio.to_thread` で別スレッドへ逃がし、理由をコメントに書く。
- 必須: SQLAlchemy の遅延読み込み（lazy load）に頼らない。関連の取得は `selectinload` などで明示し、モデルの関連は `lazy="raise"` を既定にする。`AsyncSession` は `expire_on_commit=False` で作成する。
- 必須: 外部呼び出しには、タイムアウトを付ける（`httpx` のタイムアウト、または `asyncio.timeout`）。
- 必須: `asyncio.create_task` で起動したタスクは、参照を保持し、例外を回収する（結果を待たずに放置しない）。
- 必須: 同時実行で整合性が問題になる処理は、DBの制約またはロック（`SELECT ... FOR UPDATE`、一意制約）で守る。プロセス内のロックだけに頼らない（サーバーが複数になると効かない）。
- 必須: バックグラウンド処理・定期処理は、同じ入力で複数回実行しても結果が変わらない（冪等な）作りにする。
- 推奨: 複数の独立した外部呼び出しは、`asyncio.TaskGroup` で並行実行する。ただし、同一の `AsyncSession` を複数のタスクで共有しない。

## 12. DB

- ORM は SQLAlchemy 2.0、ドライバは psycopg（v3）とし、非同期API（`AsyncSession`）で使う（11 章）。PostgreSQL の拡張 `vector`（pgvector）を使う。
- 必須: テーブル・カラム・制約は `DATABASE.dbml` を正とする。モデルの定義を変える場合は、先に DBML を更新する。
- 必須: SQL は必ずパラメータ化する。文字列連結で SQL を組み立てない。
- 必須: **会社単位の分離。** 業務データを取得・更新するクエリは、会社の条件（`company_id`、または会社を継承する親）を必ず含める。会社の条件がないクエリは、レビューで指摘する。
- 必須: トランザクションの境界は Service 層に置く。Repository の中で commit しない。
- 必須: **外部API呼び出しをトランザクションの中で行わない。** 呼び出し（Embedding生成など）を先に済ませ、その結果を使って短いトランザクションで保存する。
- 必須: 1 つの業務操作で複数のテーブルを更新する場合は、同一トランザクションにする（部分的な保存を残さない）。
- 必須: 追記専用の記録（`agent_items`、`security_events` など）は、更新・削除の処理を書かない。
- 必須: 公開済みの投稿や監査記録を通常のCRUDで削除するコードを書かない。
- 推奨: 一覧取得ではページングを使い、N+1 クエリを避ける。必要な関連は明示的に取得する。
- 推奨: 検索用の索引（ベクトル、複合）は、実際のクエリに合わせて `EXPLAIN` で確認してから追加する。

## 13. マイグレーション

- ツールは Alembic を使う。
- 必須: スキーマの変更は、必ずマイグレーションで行う。手作業でDBを変更しない。
- 必須: DBML と、対応するマイグレーションを、同じ PR で変更する。
- 必須: 1 つのマイグレーションは 1 つの目的に絞る。ファイル名は変更内容が分かる名前にする。
- 必須: DBML の Note に記載された CHECK 制約、部分ユニーク索引、ベクトル索引（HNSW）は、マイグレーションで追加する（DBML では表現できないため）。
- 必須: 本番へ適用する前に、空のDBと、本番相当のデータのDBの両方で適用を確認する。
- 必須: 破壊的な変更（列の削除、型の変更、NOT NULL の追加）は、段階的に行う（追加 → 移行 → 切り替え → 削除）。
- 推奨: 巻き戻し（downgrade）を書く。書けない変更は、その旨をマイグレーションに明記する。
- 適用は **手動** で行う。デプロイ時に自動適用しない。適用の手順と担当は、運用手順書に別途まとめる。
- 埋め込みモデルは OrcaRouter 経由の `openai/text-embedding-3-small`（1536 次元）とする。
  - `DATABASE.dbml` の `vector` 列は `vector(1536)` にし、HNSW 索引（コサイン距離、`vector_cosine_ops`）をマイグレーションで追加する。DBML の変更とマイグレーションは同じ PR に含める。
  - モデル名と次元数は設定値（`EMBEDDING_MODEL`、`EMBEDDING_DIMENSIONS`）にし、コードへ直書きしない。起動時に、設定の次元数と DB の列の次元数が一致することを検証する。
  - モデルまたは次元数を変更する場合は、全件の埋め込みを再生成し、`vector(n)` と索引を作り直す。手順は移行用のマイグレーションとスクリプトにまとめる。

## 14. テスト

- テストフレームワークは `pytest` とし、非同期テストは `pytest-asyncio` で実行する。`pyproject.toml` で `asyncio_mode = "auto"` を指定する。
- 必須: API のテストは `httpx.AsyncClient`（`ASGITransport`）でアプリを直接呼ぶ。カバレッジの計測は `pytest-cov` を使う。
- 必須: 新しい機能とバグ修正には、テストを付ける。バグ修正は、まず再現するテストを書く。
- 必須: テストの名前は、対象・条件・期待が分かる形にする（例: `test_publish_post_returns_error_when_x_api_times_out`）。
- 必須: テストは、準備（Arrange）・実行（Act）・検証（Assert）の順に書く。1 つのテストで検証する内容は 1 つにする。
- 必須: テストは互いに独立させ、実行順に依存させない。
- 必須: **外部APIを実際に呼ばない。** X、GA4、OrcaRouter、Embedding は、フェイクまたはモックへ差し替える。LLMの応答も固定のフェイクを使う。
- 必須: 時刻と乱数・ID生成は固定できる形にし、テストで固定する。
- 必須: DBを使うテストは、本番と同じ種類のDB（PostgreSQL + pgvector）で実行する。SQLite などで代用しない。テスト用DBは Docker Compose で用意する（pgvector 入りの PostgreSQL イメージを使う）。
- 必須: 次のケースは必ずテストする。
  - 異常系（入力不正、外部APIの失敗、タイムアウト）
  - 境界値（文字数の上限、空、0件）
  - **会社間の分離**（他社のデータを取得・更新できない）
  - 二重実行（同じリクエストの再送で二重に処理されない）
- 推奨: テストの種類とディレクトリ:

| 種類 | 対象 | 置き場所 |
| --- | --- | --- |
| 単体 | `domain`、`services`（依存はフェイク） | `tests/unit/` |
| 結合 | `repositories` + DB、API のエンドポイント | `tests/integration/` |

- カバレッジの目標は、新規コードの行カバレッジ 80% とする。数値よりも、上記の必須ケースの網羅を優先する。
- 禁止: テストの中で、本番の認証情報や、実在する個人情報を使うこと。

## 15. セキュリティの基本

- 必須: 外部からの入力（Request、外部APIの応答、Webから取得した内容）はすべて信頼せず、境界で検証する。
- 必須: 外部から取得したURLへアクセスする処理は、許可するスキームとホストを制限する（社内ネットワークやメタデータ用アドレスへのアクセスを防ぐ）。
- 必須: パスワードは argon2 でハッシュ化して保存し、平文で保存・ログ出力しない。
- 必須: 暗号・乱数・トークンの生成は、標準の安全な実装（`secrets` など）を使う。独自実装をしない。
- 必須: 認可の判定はサーバー側で行う。画面の表示状態に頼らない。

## 16. Git とレビュー

### 16.1 ブランチ・コミット

- ブランチ名: `feature/<内容>`、`fix/<内容>`（既存の `feature/screen-design` などに合わせる）。
- 必須: `main` へ直接 push せず、PR で merge する。
- 必須: コミットメッセージは `<種別>: <日本語の要約>` の形式にする。種別は英語の次の 6 つとする。

| 種別 | 使い方 |
| --- | --- |
| `feat` | 機能の追加・変更 |
| `fix` | 不具合の修正 |
| `docs` | 設計書・規約などの文書の変更 |
| `refactor` | 振る舞いを変えないコードの整理 |
| `test` | テストの追加・修正 |
| `chore` | ビルド、依存、CI、設定などの雑務 |

  - 例: `feat: 施策をupsertするAPIを追加` / `fix: X投稿失敗時のエラー保存を修正` / `docs: コーディング規約を更新`
  - 要約は 1 行で、変更内容と理由が分かるように書く。詳細は本文に書く。
  - スコープ（`feat(api):`）と、破壊的変更の記法は使わない。
- 必須: 1 つのコミットは 1 つの目的にする。無関係な整形を混ぜない。

### 16.2 プルリクエスト

- 推奨: 1 つの PR は、レビュー可能な大きさ（目安: 変更 400 行以内）にする。
- 必須: PR の説明に、変更の目的、変更内容、テスト方法を書く。設計書に影響する場合は、対応する設計書の変更を同じ PR に含める。
- 必須: CI（Linter、型チェック、テスト）が成功してから、レビューを依頼する。
- 承認は 1 人以上とする。

### 16.3 レビュー観点

- 設計書（DBML、API設計書）と一致しているか。
- 会社間の分離、認可、入力検証が抜けていないか。
- エラーを握りつぶしていないか。失敗を成功として扱っていないか。
- 外部API呼び出しの、タイムアウトと再試行の方針が守られているか。
- ログに機密情報が出ていないか。
- トランザクションの境界が正しいか（外部API呼び出しを含んでいないか）。
- テストに、異常系と境界値が含まれているか。
